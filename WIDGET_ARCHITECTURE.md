# Chat Widget Architecture

## Overview

The chat widget is a self-contained vanilla JavaScript snippet served as a `<script>` tag from `/api/widget/[chatbotId]`. It runs on third-party sites with zero dependencies — no React, no Tailwind, no framework. All HTML is created via `document.createElement`, all CSS is injected via a `<style>` block.

---

## File Map

| File | Role |
|------|------|
| `src/app/api/widget/[chatbotId]/route.ts` | Serves the widget JS (GET). Fetches chatbot config from DB, injects config vars, CSS, DOM creation, streaming logic, and form rendering into a single IIFE. |
| `src/app/api/chat/[chatbotId]/route.ts` | Chat API (POST). Receives messages, runs AI SDK `streamText()` with tools, streams text deltas back, and appends `__FORM__...__ENDFORM__` markers for any AI-generated forms. |
| `src/lib/ai/tools.ts` | Defines AI SDK tools. Enquiry forms become `tool()` definitions with Zod schemas built from the form's field definitions. The tool's `execute()` returns a `GeneratedFormOutput` object. |
| `src/app/api/enquiries/submit/route.ts` | Form submission endpoint (POST). Validates fields server-side, fires optional webhooks, inserts into `enquiries` table. |

## End-to-End Flow

### 1. Widget Load

```
Third-party site
  └─ <script src="https://yourapp.com/api/widget/abc123"></script>
       └─ GET /api/widget/[chatbotId]
            ├─ Fetches chatbot row (name, primary_color, widget_position, welcome_message, quick_actions)
            └─ Returns an IIFE that:
                 ├─ Injects <style> into document.head
                 ├─ Creates DOM (toggle FAB, chat window, header, messages area, input, footer)
                 ├─ Sets up event listeners (toggle open/close, send on click/Enter)
                 └─ Renders the welcome message as the first assistant bubble
```

### 2. User Sends a Message

```
Widget (browser)
  └─ sendMessage()
       ├─ Pushes { role: 'user', content } to local messages[]
       ├─ Shows thinking dots (isThinking = true → renderMessages())
       └─ POST /api/chat/[chatbotId]
            Body: { messages: last 20, visitorId, conversationId }
```

### 3. Chat API Processing (Server)

```
POST /api/chat/[chatbotId]
  ├─ Rate limit check (Upstash Redis)
  ├─ Fetch chatbot (active check, domain validation)
  ├─ Fetch owner profile (is_active, plan, message limits, billing expiry)
  ├─ Get or create conversation row → activeConversationId
  ├─ Save user message to messages table
  ├─ getModelForChatbot() → AI SDK model instance
  ├─ getChatbotTools() → { tools, enquiryFormNames }
  ├─ Build system prompt (personality + skills + RAG chunks + form instructions)
  ├─ Strip leading assistant messages (LLM providers reject assistant-first)
  └─ streamText({ model, system, messages, tools, ... })
```

### 4. AI SDK Tool Calling — How the Form is Generated

This is the key part. The enquiry form is **generated by the AI model via tool calling**, not hard-coded.

#### 4a. Tool Definition (`src/lib/ai/tools.ts`)

When `getChatbotTools()` runs, it fetches enabled `enquiry_forms` from the DB. Each form becomes an AI SDK `tool()`:

```typescript
tools[form.name] = tool({
  description: 'Collect Contact Form information. Pre-fill any fields you already know...',
  inputSchema: z.object({
    full_name: z.string(),        // built from form field definitions
    email: z.string().email(),    // fieldToZod() maps field.type → Zod schema
    address: z.string().optional(),
  }),
  execute: async (input) => ({
    _form: true,                  // marker flag
    id: form.id,                  // UUID
    name: form.name,              // e.g. "contact_form"
    display_name: form.display_name, // e.g. "Contact Form"
    fields: enrichedFields,       // field defs + generated placeholders
    prefill: input,               // AI-extracted values from conversation
    success_message: '...',
  }),
})
```

The `inputSchema` matches the form's fields. This means the AI model **decides what values to pass** based on the conversation context. If the user said "my name is John", the model will call the tool with `{ full_name: "John" }`, and those values appear as pre-filled fields.

#### 4b. System Prompt Injection

The chat route injects mandatory instructions telling the model to use the tool:

```
## Enquiry Forms — MANDATORY TOOL USE
You have these enquiry form tools: contact_form.
RULES:
1. When the user mentions: contact, enquiry, form, get in touch... MUST call the tool.
2. NEVER describe form fields in text.
3. Your ONLY text should be "Here's the form:" — then CALL THE TOOL.
4. Pre-fill any fields you already know from the conversation.
```

If form-related keywords are detected, `toolChoice: 'required'` forces the model to call a tool.

#### 4c. Custom Stream (Chat Route)

The chat route does NOT use AI SDK's default `toTextStreamResponse()`. Instead it creates a custom `ReadableStream` that:

1. Iterates `result.fullStream` (the AI SDK's full stream of events)
2. Forwards `text-delta` events as raw text chunks to the widget
3. Captures `tool-result` events where `toolName` matches an enquiry form
4. After the text stream ends, appends form data as special markers:

```
Here's the form for you:
__FORM__{"_form":true,"id":"uuid","name":"contact_form","display_name":"Contact Form","fields":[...],"prefill":{"full_name":"John"}}__ENDFORM__
```

This encoding piggybacks the structured form data onto the same text stream.

### 5. Widget Receives the Stream

```
Widget (browser)
  └─ sendMessage() → fetch() response
       ├─ Reads stream via res.body.getReader()
       ├─ Accumulates chunks into assistantMsg.content
       ├─ On each chunk: renderMessages() → updates the bubble in real-time (streaming effect)
       └─ After stream ends:
            ├─ Regex scan for __FORM__...__ENDFORM__ markers
            ├─ JSON.parse each match → formDefs[]
            ├─ Strip markers from displayed text
            ├─ Attach formDefs to the message object
            └─ renderMessages() → renders bubbles + form cards
```

### 6. Form Rendering (Widget DOM)

When `renderMessages()` encounters a message with `formDefs` and `!formSubmitted`:

```
renderMessages()
  └─ for each message with formDefs:
       └─ renderForm(formDef, parentRow)
            ├─ Creates .aichatbot-form-container
            ├─ Header: primary color gradient + form icon + display_name
            ├─ Body: iterates formDef.fields
            │    └─ For each field:
            │         ├─ Label (+ required * indicator)
            │         ├─ Input/textarea/select (type-mapped)
            │         ├─ Pre-fill from formDef.prefill[field.name] (AI-extracted)
            │         │    └─ Adds .prefilled class for visual tint
            │         └─ Error placeholder (hidden)
            ├─ Submit button
            └─ form.addEventListener('submit', handleFormSubmit)
```

### 7. Form Submission

```
handleFormSubmit(formDef, formEl, submitBtn, containerEl)
  ├─ Client-side validation (required fields, email format)
  ├─ POST /api/enquiries/submit
  │    Body: { chatbotId, formId, data, conversationId, visitorId }
  │
  └─ /api/enquiries/submit (server)
       ├─ Rate limit check
       ├─ Fetch + verify form exists and is enabled
       ├─ Server-side validation (required, email, select options)
       ├─ Fire webhook if configured
       ├─ INSERT into enquiries table
       └─ Return { success: true, message: "..." }

  Widget receives response:
  ├─ Success → replaces form card with ✓ success message
  │    (containerEl.className = 'aichatbot-form-success')
  │    Sets msg.formSubmitted = true (prevents re-render)
  ├─ Validation errors → shows field-level error messages
  └─ Network error → shows temporary error on submit button
```

## Conversation Continuity

- First message: no `conversationId` → server creates one, returns via `X-Conversation-Id` header
- Subsequent messages: widget sends `conversationId` in payload → server reuses it
- All messages (user, assistant, tool calls) are saved to the `messages` table under the conversation

## Key Design Decisions

1. **AI generates the form, not the developer.** The form structure is defined in the DB (`enquiry_forms.fields`), but the AI model decides *when* to show it and *what values to pre-fill* based on conversation context. This is native AI SDK tool calling.

2. **Custom stream, not `toTextStreamResponse()`.** We need to intercept `tool-result` events from the AI SDK's `fullStream`, extract form definitions, and append them as `__FORM__...__ENDFORM__` markers after the text. The standard streaming helper doesn't support this.

3. **Marker-based encoding.** Form data rides on the same text stream as the chat response using `__FORM__...__ENDFORM__` delimiters. The widget's regex parser extracts and strips them. This avoids needing a separate data channel or SSE protocol.

4. **Dual validation.** Forms are validated both client-side (widget JS, for instant feedback) and server-side (`/api/enquiries/submit`, for security). The server is the source of truth.

5. **Vanilla JS widget.** No framework dependencies means the widget works on any site — WordPress, Shopify, static HTML, SPAs. The entire widget is one `<script>` tag.
